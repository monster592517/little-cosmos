# 小小宇宙 · 全宇宙仿真还原 + 研究论文直达

网页版三维宇宙：**从太阳系一路连到可观测宇宙，六个尺度层级拼成一个完整宇宙**，
天体位置按真实星历实时计算。每个天体都有 3D 建模与完整物理属性，
点一下就能看资料、并且**直接跳到它的研究论文**（四源检索 + 中文翻译 + 中文进展简报）。

程序会**探测你的显卡**并自动选一套不抢资源的画质档位；数据可以一键重抓更新，
还会定期检索最新论文、把可能与本地数据冲突的结论摆到待复核队列里由你拍板。

> 数据正确性审计口径内建于 `npm run selfcheck`（离线自检，34 项）。

## 尺度阶梯：六层，各自独立

宇宙的尺度跨度是 20 个数量级——1 AU（日地距离）与 1 Gly（10 亿光年）放在同一个场景里，
浮点精度会直接崩掉（这跟"显卡不行"完全是两回事）。所以每个层级有**独立的场景、相机与长度单位**，
靠引擎的「拉远 / 拉近」在阶梯上连续切换。

| 层级 | 1 单位 = | 主要内容 |
|---|---|---|
| **太阳系** | 1 AU | 太阳、八大行星、矮行星、156 颗卫星、小天体、探测器 |
| **邻近恒星系** | 1 光年 | 3262 光年内的 10.9 万颗恒星（HYG v41）+ 471 个系外行星系统 |
| **银河系** | 1 千光年 | 银盘恒星点云、旋臂与银心结构、编目星团与星云 |
| **本星系群** | 1 百万光年 | 银河系、仙女座、麦哲伦云、主要成员与矮星系 |
| **室女座超星系团** | 1 亿光年 | 拉尼亚凯亚、室女座星系团、巨引源、程序化纤维状结构 |
| **可观测宇宙** | 10 亿光年 | 宇宙网、巨型结构（武仙-北冕座长城）、宇宙微波背景 |

**怎么切层**：顶部尺度条、右下角 ⤢ / ⤡ 按钮、`PageUp` / `PageDown`，或把滚轮一直拉到底
（滚轮顶到本层边界后会累计，攒够就跨层）。

跨尺度导航是通的：在太阳系里搜「仙女座星系」，会先切到本星系群层再聚焦它。

## 快速开始

**双击「启动小小宇宙.bat」**（图标是太阳 + 轨道环）。

- 会自动：启动本地服务（独立最小化窗口，标题 `Little Cosmos Server`）→ 用 Edge/Chrome 打开界面。
- 服务已在运行时不会重复启动，直接开窗口。
- 想停服务：关掉那个最小化的 `Little Cosmos Server` 窗口即可。

**环境要求：Node.js 18+**（只需运行时，`npm install` 不是必需的——
server 只用 Node 内置模块，clone 下来即可直接跑）。
启动器会先找同目录 `runtime\node.exe`，没有就在 PATH 里找 `node`；
两者都没有时给出带原因的报错（常见三种：zip 没解压完整 / 杀毒软件隔离了 node.exe /
SmartScreen 拦截 —— 报错里有各自的解法）。浏览器需要 Edge / Chrome 等 WebGL2。

> ⚠️ 别在压缩包里直接双击——先解压到**普通可写目录**再运行（启动器检测到
> 临时目录会拒绝启动并给出提示：server 需要在自己旁边写 logs 与 data）。
> 位置任意：所有路径在启动时按 bat 自身位置自适应，放哪个盘、哪个文件夹都行。

开发模式（自己改代码时）：

```bat
npm install                     :: 仅校验工具需要（server 运行本身零依赖）
node tools/fetch-assets.mjs    :: 抓 HYG 星表 / 系外行星 / JPL SBDB 原始数据
node tools/build-data.mjs      :: 生成 data/{stars,stars-galactic,exoplanets,small-bodies}.json
node tools/build-deepsky.mjs   :: 抓 OpenNGC 并生成 data/deep-sky.json
node tools/fetch-textures.mjs  :: 抓行星贴图（Solar System Scope）
node tools/fetch-gallery.mjs   :: 抓 NASA 真实影像并本地化
node server/server.mjs         :: 启动服务（默认 http://127.0.0.1:8787）
```

> 上面这些抓取脚本也可以**不用命令行**——在程序里打开「设置 → 数据更新中心」，
> 点一下就能跑（见下文）。

## 显卡与性能：核显 / 独显都能跑

这项目一启动就要吃显卡，而你的电脑上还有别的程序要抢。所以做了三层控制：

**1. 自动探测。** 启动时读一次 `WEBGL_debug_renderer_info`，判断你的显卡属于
Intel / AMD / NVIDIA / Apple / Qualcomm / Microsoft 哪一家，是**独显、核显还是软件渲染**，
据此选一个起始画质档位。

**2. 三档画质**（`省电 / 均衡 / 高质量`），影响渲染分辨率、抗锯齿、泛光、
粒子预算、标签预算、各向异性过滤、双缓冲等参数。档位切换**立即生效**，不需要刷新页面。

**3. 三种 GPU 偏好**（`自动 / 省电（核显） / 高性能（独显）`），以及两项省电开关：

- **离开页面时暂停渲染**——切到别的窗口/标签页就完全停帧，把显卡让给前台程序。**强烈建议保持开启。**
- **帧率上限**——限制每秒最多渲染多少帧，进一步压低功耗与发热。

> **一个必须说清楚的限制**：浏览器的 WebGL 只能**建议**用哪一类显卡，无法指定具体某一颗
> ——真正的选择权在浏览器和驱动手里。切换 GPU 偏好会重建渲染上下文（画面闪一下，属正常现象）。

另外还有两道保险：**显存回收**（只保留当前层级与相邻 ±1 层，其余彻底 dispose；不然六层全常驻会直接把标签页跑崩）
和**自动降档**（帧率持续偏低时降档；但你手动锁定过档位就不会被擅自改掉，只会提示你）。

## 数据更新中心

「设置 → 数据更新中心」（或命令面板 `Ctrl + K` 搜「更新」）里有四件事：

**① 看状态。** 14 个数据源各自的版本、条目数、体积、最后构建时间。
这些数字是**现场读**出来的（文件 stat + 数据集 meta），不是缓存字段——因为
「上次更新于某日」这类字段注定会过期，然后开始骗人。

**② 一键更新。** 更新以**管线**为单位，不以单个数据源为单位：恒星表与系外行星表
共用同一条抓取链路（`fetch-assets.mjs`），硬拆成互不相干的独立按钮只是视觉上的谎言。

| 管线 | 内容 | 产出 |
|---|---|---|
| core | 抓 HYG / NASA Exoplanet Archive / JPL SBDB，再构建 | `stars.json` `stars-galactic.json` `exoplanets.json` `small-bodies.json` |
| deepsky | 抓 OpenNGC 并构建 | `deep-sky.json` |
| textures | 抓行星贴图（含 TIFF→PNG 转换） | `web/textures/` |
| gallery | 抓 NASA 影像并本地化 | `gallery.json` |

跑的时候**日志逐行流式回传**（SSE），不用对着空白转圈。任一步失败即中止，**原有数据保持不变**。

**③ 盯前沿。** 按 9 个「高风险主题」检索 arXiv 最新预印本——卫星计数、冰巨星颜色、
探测器任务状态、系外行星大气、行星自转、星际天体、撞击风险、彗星周期、矮行星分类。

**④ 人拍板。** 采纳 / 忽略。见下节。

## 科研监测：只给线索，不下结论

用户最该警惕的是**旧知识污染**——曾广泛传播、后被推翻，但仍残留在程序里的结论。
天文学里这种情况特别多，本项目已经踩过几个（见审计报告）。所以做了这套监测。

**它做什么**：按监测主题检索 arXiv，把「可能与本地数据冲突」的论文摆进待复核队列，
标明命中关键词、以及**可能受影响的本地字段**（如 `jupiter.moons`、`TRAPPIST-1.facts`）。

**它不做什么**：假装自己能读懂论文并自动判定冲突。监测器不是大模型，它只做检索与关键词分诊。
界面里写的就是这句：**这不是自动判错。**

**为什么用「合取」筛选**：一篇论文必须**同时命中一个天体词（anchor）和一个话题词（context）**
才有资格进队列。只要求命中 `jwst` 这类泛词的话，半个人文宇宙的论文都会被塞进来
（实测：放宽门槛后，"MeerKAT 球状星团脉冲星巡天"会因为含 `orbital period` 被判为彗星论文）。
关键词匹配还带词边界——否则 `proxima` 会命中 `proximal`。

**采纳之后怎么落地**：写入 `data/overrides.json`，前端加载时按 `entityId` + 路径覆盖字段值。
**自动流程永远不会直接改写程序数据**——这是硬约束。覆盖表本身也是可撤销的。

## 位置是真实的

| 天体 | 位置来源 | 精度 |
|---|---|---|
| 八大行星、冥王星 | astronomy-engine 的 **VSOP87** 行星理论 | 与 JPL 星历偏差约 1 角分 |
| 月球 | **ELP2000-82B** 月球理论 | 同上 |
| 木卫一~四 | 木星卫星专用模型（含轨道共振） | 轨道半径误差 < 0.2% |
| 其余卫星（150 余颗） | 真实平均轨道要素（a / e / i / 周期取自 JPL SSD） | 相位示意，半径与周期真实 |
| 小行星、彗星、海外天体（90 余颗） | **JPL SBDB** 实测轨道要素（含历元） | 二体推进，短期内高精度 |
| 邻近恒星（10.9 万颗） | **HYG v41**（汇编自 Hipparcos / Gaia / Gliese） | 赤道 J2000 直角坐标 |
| 编目深空天体（1.29 万条） | **OpenNGC** | 河外星系距离由红移按哈勃定律推算 |
| 探测器 | 在轨者按真实半长轴/周期环绕；着陆者按着陆点经纬度贴在地表；日心飞行者按官方公布的日心距离与方向定位 | 见下 |

所有天体统一在**黄道 J2000 坐标系**内计算，所以行星、卫星、小行星在同一个场景里严格对齐。
**轨道线是用真实位置采样出来的**，因此天体永远落在自己画出的轨道上。

银河系层要额外做一次坐标转换：HYG 用的是**赤道 J2000**，需要旋转到**银道坐标系**
才能把 10.9 万颗恒星贴到银盘上、让太阳落在猎户臂内侧的正确位置。

自带交叉校验工具（两套彼此独立的算法互比 + 若干人工参照值）：

```bat
node tools/verify-ephemeris.mjs
```

实测结果（2026-09-09）：

```
J2000 地球日心黄经：VSOP87 100.3784° vs Standish 100.3802°（差 0.0018°）
2026-09-09 太阳视黄经 = 165.98°（9 月上旬太阳位于室女座 ≈166°，人工核对通过）
月球地心距离 = 370,272 km（真实范围 356,500–406,700 km）✓
木卫一轨道半径 = 422,416 km（真实 421,800）· 木卫四 = 1,883,387 km（真实 1,882,700）
两法最大角偏差 518.8″ = 0.14°（这是 Standish 近似表本身的误差，不是程序的）
```

## 探测器

按「它现在在哪」归位，而不是统一堆在一个列表里：

| 类型 | 表现 |
|---|---|
| 在轨环绕（朱诺号、LRO、MRO、MAVEN、天问一号…） | 画出一条真实的环绕轨道，探测器沿轨道实时运行 |
| 已着陆 / 已坠毁（毅力号、好奇号、阿波罗、嫦娥、惠更斯、菲莱、NEAR…） | 贴在着陆天体的对应经纬度上，用十字准星标出着陆点 |
| 日心飞行（旅行者 1/2 号、新视野号、帕克、JUICE、欧罗巴快船、露西…） | 按官方公布的日心距离与方向定位，并画出「发射 → 引力弹弓 → 当前位置」的飞行轨迹 |
| 任务已结束（伽利略、卡西尼、黎明号、拂晓号…） | 归到目标天体下，标注真实状态 |

选中任何一个天体，镜头都会平滑推进到它的**全貌图**——球体大约占据画面高度的 60%。

## 3D 建模与贴图

**太阳系内全部 253 个天体都有三维模型**——太阳、八大行星、5 颗矮行星、156 颗卫星、
86 个小天体（主带 / 特洛伊 / 半人马 / 柯伊伯带 / 彗星 / 星际天体）。

- **真实高清贴图**：太阳与八大行星用 Solar System Scope 8K 贴图；
  **冥王星、卡戎、土卫一~五、土卫六、土卫八、海卫一用 NASA / USGS 官方全球马赛克原图**；
  其余卫星、矮行星、小天体用 Celestia Content 的 NASA / USGS / JPL 全球影像。
- **显存预算**：全场景约 330 张纹理，按「全景取景时球体约占画面高 60%」倒推分辨率上限，
  总显存约 330 MB。同时监听 `webglcontextlost` 自动重建场景。
- **法线贴图**：对细节不足的影像（Voyager 2 拍的天卫、Cassini 拍的小卫星等 35 个天体），
  由灰度梯度 + 程序化撞击坑生成法线贴图，在真实光照下表现出地形起伏。
- **建模来源标注**：每个天体的详情页底部有「3D 建模与影像来源」，写明贴图来自哪套影像、
  分辨率、原始影像、授权，并给出建模所用贴图的缩略图。
- **影像类型标注**：每张图都标出类型——**原始影像** / **后处理增强** / **科学模拟·艺术家重建**。
- **天王星 / 海王星的颜色**：早期旅行者 2 号照片里海王星是深蓝色，那是相机传感器经过木星辐射带
  **受损** + 对比度增强处理造成的失真。按 Irwin et al. 2024（MNRAS）的结论，两颗冰巨星其实都是
  **淡淡的青蓝色**，海王星只比天王星略偏蓝、并不更"深"。本项目对贴图做了重定色与色度压制。
- **行星环**：按真实内外半径与环缝结构绘制，随环面倾角变化。
- **小天体形状**：按真实特征生成——爱神星与丝川的「花生」、克丽奥佩特拉的「狗骨头」、
  贝努与龙宫的「陀螺」、67P 的「橡皮鸭」。

## 天体属性

点击场景里的天体（哪怕它只是一个光点也能点中），或点标签、或用搜索框，都会打开属性面板：

- **实时状态**：日心黄经/黄纬、距太阳、距地球、光行时、轨道速度、视星等、相位、视直径、环面倾角。
- **轨道要素**：半长轴、偏心率、倾角、升交点黄经、近日点黄经、近/远日点距离、公转周期。
- **物理参数**：赤道半径、直径、质量、密度、表面重力、逃逸速度、自转周期、轴倾角、
  反照率、视星等、绝对星等、光谱型、光度。
- **环境与组成**：平均温度、温度范围、核心/日冕温度、大气成分与气压、年龄、内部结构分层。
- **太阳专属**：质量占比、磁场、太阳风、活动周期、聚变速率、光子旅程、距银心距离与绕行周期。
- **探测器专属**：任务状态、运行机构、发射日期、位置类型、目标天体、着陆点经纬度、日心距离。
- **发现与探测**：发现年份/发现者/发现方式，以及历次探测任务。
- **人工修正标记**：被 overrides 改过的字段会标明来源与时间。

## 研究前沿

「研究」按钮或属性面板里的「查看最新研究进展」，用自建检索器同时查询
**arXiv · OpenAlex · Crossref · Semantic Scholar**；中文关键词自动转英文；
摘要可一键译为中文；「生成进展简报」把最新论文压成中文要点。

**不依赖任何付费 API / API Key：**

| 环节 | 实现 |
|---|---|
| 中文检索词 → 英文 | 翻译引擎转写，失败时退回内置天文术语表 |
| 摘要翻译 | ① 浏览器内置翻译（本地模型，可离线）→ ② 本地服务代理的公共翻译接口 → ③「整页翻译」交给浏览器 |
| 进展简报 | **本地抽取式摘要**：按关键词/位置/线索词给原句打分，按「核心结论 / 方法与观测 / 争议 / 下一步」归类，每条标注来源论文编号，**不调用任何在线大模型、不编造内容** |

翻译与简报结果都会落盘缓存，重复查看不再联网。

## 数据正确性审计

天文学最容易出的一类错误是**旧知识污染**：某个结论曾经广泛传播、后来被推翻或修正，
但网上到处都是旧版本，程序里也就跟着错了。所以做了一轮彻头彻尾的审计。

- **方法**：逐字段抽取事实项 → 标记随时间漂移的高风险项 → 联网逐一核查（**只采信**
  NASA / ESA / JAXA / JPL / IAU / MPC / 官方任务页 / 近三年同行评议论文）；
  拿不准的放入「待观察」，**不硬改**。
- **结果**：**17 条修正已应用**（5 高 / 10 中 / 2 低），19 条已核查无误，5 条待观察。
- **可复现**：修正不是手改的，而是固化成 `tools/apply-audit-fixes.mjs`——
  每条都有出处，`find` 片段必须**唯一命中**，否则脚本报错退出，不会静默改错行。

几个例子：

| 项目 | 原值 | 修正为 | 依据 |
|---|---|---|---|
| 木星卫星数 | 95 | **115** | NASA 行星卫星计数（2026-04） |
| 土星卫星数 | 274 | **293** | NASA / NAOJ 2026-06，MPEC 2026-F14 |
| 拂晓号状态 | 在轨运行 | **任务已结束（2025）** | JAXA 2025-09-18 终止公告 |
| 贝努撞击年份 | 2135 年 | **2182-09-24** | JPL CNEOS Sentry |
| 海尔-波普回归周期 | 约 4300 年 | **约 2400–2530 年** | JPL SBDB |
| 土星自转周期 | 10.656 h（Voyager 旧值） | **10.5606 h** | Mankovich et al. 2019（Cassini 环震学） |
| 海王星标记色 | 深蓝 `#4a6fd4` | **淡青蓝 `#7aa5e0`** | Irwin et al. 2024 |
| 探测器参考历元 | 常量 `2461261.5`（注释却写 2026-09-09） | **`2461292.5`** | 前者换算回来是 2026-08-09，差一个月，所有日心探测器被多推进约 0.3 AU |

完整清单见 [`自检维修手册.md（原《审计报告-数据正确性.md》）`](./自检维修手册.md) 与
机器可读的 `data/audit-findings.json`。

> ⚠️ **卫星数量属于高速变动数据**：2025–2026 年土星、木星仍在批量确认新卫星。
> 建议每年重跑一次审计，或用「数据更新中心」的科研监测盯住这个主题。


**打包完成 ≠ 能用。** `check-package.mjs` 补的就是这一步：用**包内自带的** `runtime/node.exe`
（不是系统 Node）真起一遍服务，确认 health / 日志自建 / 自检 / 静态资源 / 404 语义都对，
并且**包内自检必须是零故障**——交付物一解压就自己报红字，那是最难看的失败方式。

它同时守着一件容易出事的事：**不该进包的东西一个都没进去**（`.trash` 隔离区、`logs` 运行日志、
`.workbuddy` 外部工具数据、`node_modules`）。这条以前只靠"我复制的时候没列它"侥幸成立——
哪天有人加一句 `copyTree(ROOT)`，隔离区就跟着发布了。

**端口约定**：测试用 **8791 / 8793 / 8794**，别用 8787 —— 那是日常服务默认端口，撞上会让你分不清是测试挂了还是你自己的服务挂了。

`check-http.py` 守的是一件很容易被顺手改坏的事：**不存在的静态资源必须返回 404**。
早先的 SPA 回退会把任何找不到的路径回成 `200` + `index.html`，于是贴图名写错就会静默变成
「浏览器拿 HTML 当图片解码」——画面黑一块，却看不到任何报错。这条测试就是防止它回来。

`selfcheck.mjs` 守的是另一类更容易被忽略的事：**登记表和现实是否一致**。
真实案例——`data/sources.json` 里写着影像库管线的产出目录是 `web/gallery/`，实际代码写的是
`web/images/`。谁都没报错：管线照跑、页面照开、影像照显示，**只是登记表在骗人**。
自检的 `data.registry-honesty` 专门核对每条管线声明的产出目录、每个步骤的脚本文件、
每个数据集的管线归属是否真实存在。

`shell.point-materials` 守的是另一类：**不报错的缺陷**。`PointsMaterial` 缺 `map` 时每个点会被画成
硬边方块（不是圆点），不崩溃、不进日志，只是安静地难看——本项目因此踩过两次
（`solar.js` 的奥尔特云、`supercluster.js` 的纤维结构）。判的时候会**先剔掉注释**再找 `map:`，
否则注释里提一句 `map` 就会让它假通过。

**但检查本身也会失灵**，所以还有 `check-selfcheck.mjs`：它在临时目录里造一堆假项目、注入已知故障
（点云缺 `map` / npm 脚本指向空气 / 核心文件缺失 / 旧名未标记），断言每条检查**真的抓得住**，
再喂合法样本断言**零误报**。理由很直白——**一条永远报绿的检查，比没有检查更糟**，
它把「全绿」变成了假信号。

`naming.outside-refs` 守的是**扫描边界之外**的那类：桌面快捷方式住在**仓库外面**，
任何「全仓库更名」都扫不到它，于是产品一改名它就变成指向空气的图标 ——
双击只得到一句「找不到 `<它自己记着的那个旧文件名>`」。它靠 `tools/install-shortcut.mjs` 核对
四个路径是否**真实存在**，并恒为 `warn`（快捷方式坏了不影响程序能不能用）。
注意反向的坑：便携版解压在别处时，快捷方式**理应**指向原来那份目录，
只有目标**真的不存在**才算坏 —— 否则便携包每次体检都报警，用户很快就学会无视自检了。

同一处还有两个细节值得知道：**摘要是从 `--check` 的原始输出派生的**（不写死吉言），
所以「指向本目录」和「指向另一份副本」措辞不同、并明说核对的是谁；
而这条检查在跳过（包里没带工具 / 根目录没有唯一的 `启动*.bat`）时返回 `ok`，
所以在**源码仓库**里它有可能悄悄不跑 —— `check-selfcheck.mjs` 为此钉了三颗钉子，
其中一颗专门**反向验证跳过分支的措辞能被过滤认出来**。改文案时记得两头一起改。

`env.trash-size` 守的是**磁盘**：本项目的删除一律走隔离区，而 `tools/package.mjs`
每跑一次就往里放一份约 130 MB 的旧暂存目录，隔离区**只进不出**。超过 1 GB 它就提醒一次，
并给出可直接照做的处置命令。它**最高只 warn** —— 占磁盘不影响程序能不能用，
误报只会训练用户无视自检。顺带记一个本机的硬事实：**删一个文件要约 50 ms**
（临时目录里 64 字节的小文件也一样，换 API 没用），所以任何批量删除都必须打进度，
否则在这台机器上它长得跟卡死一模一样。

`check-scales.py` 的常用选项：

| 选项 | 作用 |
|---|---|
| `--levels=solar,galaxy` | 只测指定层级，做快速冒烟（十几秒出结果） |
| `--level-timeout=25000` | 单层等待上限（毫秒），默认 40000 |
| `--url=...` | 换目标地址 |
| `--shots` | 顺便截图到 `shots/` |
| `--no-log` | 不写 `shots/scale-test.log` |

**为什么这个测试看起来"很慢"**：它跑在 SwiftShader 软件渲染（CPU 模拟 GPU）上。
引擎的层级过渡按每帧 dt 累加（上限 0.1s/帧），在软件渲染的低帧率下，
一次 1.05s 的过渡要 **2~6 秒**真实时间，六层加起来一分钟左右是正常的。

为了让"正常地慢"不被误判成"卡死"，脚本做了三件事：

1. **每一行都 flush，并同时追加写入 `shots/scale-test.log`**——进程即使被外部杀掉，
   已经跑过的部分也不会丢。
2. **每个阶段先打印 `[n/N] 阶段名`**，结束时打印耗时。
3. **等层级切换时每 2 秒打一个点**（`· 等待层级切换···`），肉眼能确认它还活着。

实测（2026-09-11）：六层全绿，**总用时 60.1s**，0 console 错误。

## 维护与自检

这个项目的交付标准是：**每次改动要同时维护四类东西，否则算没做完**。

| 交付物 | 文件 | 给谁看 |
|---|---|---|
| **日志系统** | `server/lib/log.mjs`，落 `logs/server-YYYY-MM-DD.jsonl` | 出问题时定位。服务端 + 前端都有轨迹 |
| **自检 + 维修手册** | `server/lib/selfcheck.mjs` + `自检维修手册.md` | 症状 → 判据 → 根因 → 处置，**每条都给可执行命令** |
| **操作手册** | `操作手册.md` | 界面怎么用、参数什么意思、**边界在哪** |
| **坑与雷点** | `坑与雷点.md` | 每条标注「固化成什么了」——固化不了的算负债 |

### 日志

```json
{"t":"2026-09-11T07:12:03.114Z","level":"warn","scope":"server","msg":"静态资源缺失","data":{"path":"/textures/xxx.jpg"}}
```

固定五字段 `t` / `level` / `scope` / `msg` / `data`，一行一条 JSONL。**人能读，脚本也能直接解析**——排查时不用再写正则去啃自由文本。

四条设计取舍：

1. **同步写盘**（`appendFileSync`）。日志量本来就小（每天几百行），而"崩溃后再也读不到日志"是最糟的失败模式。用一点性能换「进程被杀也留得下最后一行」。
2. **目录不可写就降级为仅控制台，绝不因为写不了日志把服务干死。**
3. **JSONL 而非自由文本。** 排查时不该花时间解析日志格式。
4. **内存环形缓冲 2000 条**供接口即时取；进程重启后缓冲是空的，自动退回读文件。

日志保留 14 天，跨天时自动清理。

### 自检

七组：**运行环境** / **程序骨架** / **数据集与登记表** / **人工覆盖与监测** / **本地服务** / **性能与显卡** / **命名一致性**。

> **性能与显卡**这一组只有一条 `perf.gpu-hybrid`，而且**最高只判 warn**。
> 它查的是一件很容易被误解的事：混合显卡笔记本上，浏览器默认跑**核显**，
> 而**核显没有自己的显存 —— 它的「显存」是从系统内存借的**。
> 于是「把负载放到显存上」在核显上等于「放到系统内存上」，与初衷正好相反。
> 这是续航取舍、不是缺陷，所以不判 error（误报会训练用户无视自检）。
> 配套工具：`node tools/gpu-preference.mjs`（读 / 设 / 还原）、
> `py -3.13 -X utf8 tools/perf-probe.py`（**唯一可信**的后端判据）。
> 详见 [操作手册](操作手册.md) 的「显卡与性能」。

分级口径只管一件事——**现在还能不能正常用**：

- `error` = 功能已经坏了 / 会立刻坏
- `warn` = 还能用，但正在腐坏
- `ok` = 没事

不搞「健康度百分比」这种自欺欺人的数字。

**每一条检查都必须带 `fix`** —— 一句可以直接照做的话。只报「有问题」却不告诉你怎么办的检查，等于给车主看仪表盘却把修理厂地址抠掉。

三个入口跑同一套内核：

```bat
node tools/selfcheck.mjs                  :: 命令行（不依赖服务）
node tools/check-server.mjs --port=8793   :: 端到端（自己拉服务打接口再关掉）
:: 界面：设置 → 打开数据更新中心 → 系统自检 → 运行自检
```

界面上的自检是**点了才跑**，不是打开面板就跑。一次自检要遍历数据集、解析十来个 JSON、扫关键目录，1–3 秒——放进面板打开路径上就等于每次开面板都卡一下。**新增功能请沿用这条规矩。**

### 两条防「静默故障」的机制

**① 登记表要接受拷问。** `data.registry-honesty` 会核对 `sources.json` 里每条管线声明的产出目录、每个步骤的脚本文件、每个数据集的管线归属**是否真实存在**。

防的是最隐蔽的一类故障：程序不报错，只是悄悄少了一块数据。真实案例——登记表写着影像库产出在 `web/gallery/`，实际代码写的是 `web/images/`。

> **登记表和现实不符时，永远改登记表去匹配现实**，不要反过来把代码改歪去迁就一份写错的表。

**② 命名残留的豁免要自证，不要维护清单。** `naming.legacy` 扫描旧项目名残留时，不维护中央豁免清单（清单会腐烂——改代码的人不会记得去更新它）。改成**让源码自己声明**：行内带「更名遗留 / legacy / 旧键 / 有意保留」任一字样就跳过。

```js
/** 更名遗留：旧版本存画质偏好用的键。只读兼容一次，读到就迁到新键并清掉。 */
const LEGACY_LS_KEY = 'lss.gpu.v1';
```

豁免与被豁免的东西待在一起，不会走散。

## 科学说明

1. **尺度分层**：六个层级的长度单位相差最多 20 个数量级，**必须在不同场景里渲染**。
   跨层时引擎会重建场景并回收非相邻层的显存，这是设计需要，不是实现偷懒。
2. **天体大小**：默认「视觉增强」把半径按 `r^0.45` 压缩；底栏「真实比例」可切回真实半径
   ——那时行星真的会小到看不见，这才是物理真相。
3. **卫星轨道**：视觉模式下按母星半径的 2.4–5.8 倍按对数分级放大（半径与周期保持真实）。
4. **卫星相位**：木卫一~四与月球用真实模型，其余卫星的**相位**为示意值，半径/周期/倾角真实。
5. **行星位置**：VSOP87 与 JPL 的偏差约 1 角分，肉眼与望远镜实景无法区分。
6. **深空天体距离**：银河系内天体按类型取代表性距离；河外星系**仅当红移 z ≥ 0.004**
   （cz ≥ 1200 km/s）时才按哈勃定律 H₀=70 推算——红移更小的近距星系受本动速度主导，
   哈勃定律在该尺度失效，这些天体的距离**留空**而不是硬算一个错数（实测有 728 个这样的星系）。
7. **粒子与截断**：深空目录按亮度截断（目录显示前 260 条、场景按粒子预算抽样）；
   「全部可观测天体」在物理上不可实现——宇宙里有上万亿个星系，
   本项目的做法是**真实编目 + 程序化补全**，并如实标注哪些是编目数据、哪些是代表性分布。
8. **论文检索与监测**：结果是各开放源实时返回的元数据。科研监测只做检索与关键词分诊，
   **不做语义冲突判定**，采纳与否由人决定。

## 〇、先说清楚「专家调用」是什么意思

天文学里没有「打个电话问专家」这种接口。真正可调用的「专家」是这三层，可靠性依次递减：

| 层级 | 是什么 | 能不能自动调用 |
|---|---|---|
| **① 官方数据服务** | NASA / ESA / JPL / IAU 的公开 API | ✅ 可以直接编排进脚本 |
| **② 权威数据源维护者** | 具体到人的开源项目维护者、官方任务团队 | ⚠️ 只能「通过其发布的数据」间接调用 |
| **③ 论文作者与机构** | 同行评议论文的作者群、任务 PI | ❌ 不可调用，只能作为**结论的出处**引用 |

**本项目只把 ① 写进自动管线，把 ② ③ 作为人工审计时的核对依据。** 这是刻意的边界：
自动流程永远不引用「某专家说」，只引用「某机构在某日发布的数据」。

## 二、权威数据源 —— 可编程调用的官方接口

### 2.1 系外行星

| 源 | 端点 | 许可 | 本项目用途 |
|---|---|---|---|
| **NASA Exoplanet Archive · TAP** | `https://exoplanetarchive.ipac.caltech.edu/TAP/sync` | 公有领域 | `data/exoplanets.json` 的唯一来源 |
| 同上 · `pscomppars` 表 | ADQL `select ... from pscomppars` | 公有领域 | 每个行星系统的**综合参数**（行星 + 宿主恒星） |
| 同上 · `stellarhosts` 表 | ADQL `select ... from stellarhosts` | 公有领域 | 宿主恒星的**恒星参数**（48,792 行），用于推算校验 |
| **太阳系外行星百科全书** | `https://exoplanet.eu/` | 需看站点条款 | **交叉校验源**（巴黎天文台维护，与 NASA 口径时有差异） |

**可直接粘贴的调用示例**（统计各半径下有多少行星系统）：

```bash
curl -sG "https://exoplanetarchive.ipac.caltech.edu/TAP/sync" \
  --data-urlencode "query=select count(distinct hostname) as n from pscomppars where sy_dist < 1000" \
  --data-urlencode "format=json"
```

> **本项目的半径选择（2026-09-11 实测）**：

| 半径 | 行星数 | 宿主恒星数 |
|---|---|---|
| 40 pc（旧） | 758 | 471 |
| 100 pc | 1,569 | 1,055 |
| **1000 pc（现采用）** | **5,217** | **3,823** |
| 全表（不分距离） | 6,360 | — |

选 1000 pc 的理由：**邻近恒星系层的恒星表本身就铺到 3262 光年（≈1000 pc）**，
行星数据只到 40 pc 会在这层留下大片「有恒星、无从判断」的空洞。

### 3.3 从「机构」到「人」的边界

项目里出现具名个人，只有两种情况：**开源数据集的维护者**（他们把名字写进了仓库许可），
以及**论文作者**（用于标注结论出处）。除此之外**不引入任何具名「专家意见」**——
因为无法验证、无法追责，且极易成为「旧知识污染」的传播通道。

## 四、本项目**不采信**的来源（排除清单）

按 `审计报告-数据正确性.md` 的既定规则：

- ❌ 博客、自媒体、内容农场
- ❌ AI 生成的科普内容
- ❌ 无出处维基式汇编（**本次实测再次命中**：一份把木星写成 95、土星写成 274、海王星写成 19 的
  「卫星数」网页，正是典型的过期汇编——它同时错三项，因此整页作废）
- ❌ 二手汇总表（实测：一份 2026-05 的 JPL 汇总表把新视野号写成 63.3 AU，
  与任务方自述的 65–66 AU 相距 11 AU/年，明显不合理）
- ⚠️ 超过 3 年的技术性数据（卫星计数、探测器状态、系外行星大气结论）

**判断口径**：一个来源只要在**任一**已核实项上出错，就降级为不可信来源，不再引用。

## 五、怎么把新数据源接进来（操作路径）

1. **先登记身份** → 写入 `data/sources.json` 的 `datasets` 或 `monitors` 数组
   （提供方 / 许可 / 端点 / 所属管线 / 更新节奏 / 能否自动重抓）。
2. **抓取脚本只写 `data/raw/`** → 脚本落原始数据，不改动 `web/js/data/` 下的人工整理表。
3. **构建脚本产出 `data/*.json`** → 先写临时文件，校验通过再替换；失败保留原数据并如实报错。
4. **元数据不缓存** → 「最后构建时间 / 记录数 / 体积」永远现场读（文件 stat + meta），
   不写进 `sources.json`。写死的日期字段注定过期，然后开始骗人。
5. **跑回归** → 先 `node tools/selfcheck.mjs`（`data.registry-honesty` 会核对你新写的产出目录
   与步骤脚本是否**真的存在**——登记表和现实不符时，永远改登记表去匹配现实），
   再跑 `tools/check-http.py`（静态资源）、`tools/check-datacenter.py`（数据中心）、
   `tools/check-scales.py`（六层尺度）；最后 `tools/check-selfcheck.mjs`（验证这些检查本身没失灵）。
6. **科研监测只产线索** → 自动流程永不直接改写程序数据；人工在数据中心点「采纳」才写 `overrides.json`。
